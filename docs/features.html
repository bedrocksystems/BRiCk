Language Support

The BRiCk program logic is aimed to be a formalization of pragmatic C++. Its feature set is guided by the requirements of low-level program verification and also some pragmatic considerations.

Status

This page describes BRiCk and cpp2v as of October 2026. Each entry links to its tracking issue where one exists. The CHANGES.md file at the repository root lists breaking changes.

A C++ construct that BRiCk does not fully support falls into one of the following categories, from most to least disruptive:

Rejected by cpp2v

cpp2v stops with a fatal error. No part of the translation unit can be verified.

Unsupported declaration

cpp2v emits Dunsupported for a type and continues. Functions whose code needs that type cannot be verified; other functions in the translation unit are unaffected.

Unsupported syntax

cpp2v emits Eunsupported, Sunsupported, Tunsupported, or Bunsupported. These have no semantics: a proof that reaches one gets stuck.

No semantics

cpp2v translates the construct faithfully, but the program logic has no rule for it. A proof that reaches it gets stuck.

Partial

The program logic covers the construct, but not all of its behaviors, or covers it with a documented restriction.

skylabs.lang.cpp.syntax.supported checks a translation unit for many of these constructs.

Floating point arithmetic and comparisons are supported for IEEE-754 formats (half, single, double, and quad precision), with semantics given by Flocq. x87 long double values are abstract.

Soundness Caveats

The following are known ways in which a proof can be weaker than it appears.

  • Exceptions. Function calls are assumed not to throw.

  • Member functions are modeled as functions. Exploiting this requires reinterpret_cast.

  • Defaulted functions. BRiCk relies on the semantics of defaulted functions (default constructors, assignment operators, etc.) as generated by Clang. A different compiler may generate different, still correct, code that invalidates your proof.

Other known soundness bugs, and the pull requests that fix them, carry the soundness label.

Trusted Base

The program logic is stated axiomatically: rocq-skylabs-brick/theories contains about 450 Axiom declarations. The models under theories/lang/cpp/model currently contain 8 Admitted lemmas (simple_pred.v, inductive_pointers.v, inductive_pointers2.v).

Deviations from the Standard

In certain instances, BRiCk’s semantics deviates from the C++ standard.

  • BRiCk’s semantics do not currently permit “pointer zapping”. See Assumptions beyond the standard.

  • BRiCk uses Tnum sz sgn to represent all integer types rather than the standard types char, short, int, long, long long.

  • BRiCk is based on the Clang front-end IR. We believe that this is a reasonable proxy for source-level C++.

  • The BRiCk program logic assumes that the abstract syntax tree is well-typed and uses this assumption to avoid performing type checking within the semantics. If you are using cpp2v to generate the AST, then Clang will ensure that the syntax tree is well typed.

Toolchain Requirements

  • cpp2v requires LLVM 20 through 22 (as tested in CI). The release images use LLVM 22.

  • Generate the AST with exactly the same Clang flags and target as your build. The AST fixes implementation-defined behavior, such as the sizes of integer types (whether incrementing a long holding 0x7fffffff overflows), and the code Clang generates for defaulted functions.

Extensions to the Standard

BRiCk also extends the C++ standard in limited ways to make low-level program verification possible. For example, inter-operation with assembly (see Assembly Interoperation), sharing data across address spaces, etc. We believe that our extensions are conservative and characterize the way that low-level programmers rely on compilers to work.

We plan to support weak memory C++ in the future based on other work in Iris.
